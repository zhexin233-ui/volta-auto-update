## Context

当前用户使用 Volta (v2.0.2) 管理多个 Node.js 开发工具，包括：
- @openai/codex（当前 0.89.0，最新 0.92.0）
- @google/gemini-cli（当前 0.25.2，最新 0.26.0）
- @anthropic-ai/claude-code（当前 2.1.19，最新 2.1.22）

手动检查和更新这些工具需要：
1. 运行 `volta list all` 查看当前版本
2. 访问 npm 网站或运行 `npm view <package> version` 查看最新版本
3. 对每个过期的包运行 `volta install <package>@latest`

这个过程繁琐且容易遗漏。需要一个自动化脚本来简化这个流程。

## Goals / Non-Goals

**Goals:**
- 创建一个可执行的 shell 脚本，自动检查和更新三个指定的工具
- 提供清晰的命令行输出，显示检查和更新进度
- 支持 macOS 系统，可通过终端或双击执行
- 处理常见错误场景（网络失败、工具未安装等）

**Non-Goals:**
- 不支持 Windows 或 Linux 系统（当前仅针对 macOS）
- 不提供配置文件来自定义要检查的工具列表
- 不提供 GUI 界面
- 不实现版本回滚功能
- 不支持检查 Volta 本身的版本更新

## Decisions

### 决策 1：使用 Bash Shell 脚本
**选择：** 使用 Bash 脚本而非 Node.js 或 Python 脚本

**理由：**
- macOS 默认包含 Bash，无需额外依赖
- 直接调用 volta 和 curl 命令更简单
- 脚本体积小，启动快
- 易于创建 .command 文件供双击执行

**替代方案：**
- Node.js 脚本：需要额外的 package.json 和依赖管理
- Python 脚本：macOS 默认 Python 版本可能不一致

### 决策 2：使用 npm registry API 查询最新版本
**选择：** 直接调用 `https://registry.npmjs.org/<package>/latest` API

**理由：**
- 返回 JSON 格式，易于解析
- 无需认证，公开可访问
- 响应速度快，数据可靠
- 避免依赖 npm CLI（可能未安装或版本不一致）

**替代方案：**
- 使用 `npm view <package> version`：需要 npm CLI，且输出格式可能变化
- 爬取 npmjs.com 网页：不稳定，易受页面结构变化影响

### 决策 3：使用 jq 或纯 Bash 解析 JSON
**选择：** 使用纯 Bash + grep/sed 解析 JSON

**理由：**
- 避免依赖 jq（用户可能未安装）
- JSON 结构简单，只需提取 version 字段
- 使用 grep/sed 足够可靠

**替代方案：**
- 使用 jq：更优雅，但需要额外安装
- 使用 Python：增加脚本复杂度

### 决策 4：脚本结构
**选择：** 分为三个主要函数：
1. `check_version()` - 检查单个工具的版本
2. `update_tool()` - 更新单个工具
3. `main()` - 主流程控制

**理由：**
- 模块化设计，易于测试和维护
- 可复用函数逻辑
- 清晰的职责分离

### 决策 5：错误处理策略
**选择：** 继续执行策略（fail-soft）

**理由：**
- 一个工具更新失败不应阻止其他工具更新
- 显示错误信息但继续处理下一个工具
- 最后显示摘要，列出成功和失败的工具

**替代方案：**
- 遇到错误立即退出（fail-fast）：用户体验差，需要多次运行

## Risks / Trade-offs

### 风险 1：npm registry API 不可用
**风险：** 网络问题或 npm registry 服务中断导致无法获取最新版本

**缓解措施：**
- 设置 curl 超时时间（10 秒）
- 显示清晰的错误信息
- 跳过该工具，继续处理其他工具

### 风险 2：JSON 解析失败
**风险：** npm registry API 返回格式变化或非预期响应

**缓解措施：**
- 检查 curl 退出码
- 验证 JSON 响应包含 version 字段
- 解析失败时显示原始响应（调试用）

### 风险 3：volta install 失败
**风险：** 网络问题、权限问题或 Volta 本身故障导致安装失败

**缓解措施：**
- 检查 volta install 退出码
- 显示 volta 的错误输出
- 继续处理下一个工具

### 风险 4：版本比较逻辑错误
**风险：** 语义化版本比较可能出错（如 1.10.0 vs 1.9.0）

**缓解措施：**
- 使用简单的字符串比较（对于大多数情况足够）
- 如果需要精确比较，可以使用 sort -V 命令

### 权衡 1：硬编码工具列表 vs 配置文件
**选择：** 硬编码三个工具的包名

**权衡：**
- 优点：简单，无需解析配置文件
- 缺点：添加新工具需要修改脚本
- 理由：当前需求明确，三个工具固定，配置文件增加复杂度

### 权衡 2：详细输出 vs 简洁输出
**选择：** 详细输出，显示每个步骤

**权衡：**
- 优点：用户清楚了解脚本在做什么，便于调试
- 缺点：输出较多，可能显得冗长
- 理由：自动化脚本需要透明度，用户应该知道发生了什么

## Implementation Plan

### 文件结构
```
/Users/zhexin/web/volta-auto-update/
├── update-volta-tools.sh          # 主脚本
└── update-volta-tools.command     # macOS 双击执行版本（符号链接或副本）
```

### 脚本主要流程
1. **初始化**
   - 显示欢迎信息
   - 定义工具列表（包名和显示名）
   - 初始化计数器（成功、失败、跳过）

2. **版本检查循环**
   - 对每个工具：
     - 使用 `volta list all` 获取当前版本
     - 使用 curl 查询 npm registry 获取最新版本
     - 比较版本号
     - 记录需要更新的工具

3. **显示版本对比表格**
   - 格式化输出当前版本 vs 最新版本
   - 高亮需要更新的工具

4. **更新循环**
   - 对每个需要更新的工具：
     - 执行 `volta install <package>@latest`
     - 检查退出码
     - 显示成功或失败信息
     - 更新计数器

5. **显示摘要**
   - 显示成功、失败、跳过的工具数量
   - 列出失败的工具（如果有）

### macOS .command 文件支持
- 创建 `update-volta-tools.command` 文件
- 内容与 `.sh` 文件相同
- 设置可执行权限：`chmod +x update-volta-tools.command`
- 在脚本末尾添加 `read -p "按任意键关闭..." -n1` 以保持窗口打开

## Open Questions

1. **是否需要在更新前显示确认提示？**
   - 当前设计：自动更新所有过期工具
   - 替代方案：显示需要更新的工具列表，询问用户是否继续
   - 建议：先实现自动更新，如果用户需要可以后续添加确认步骤

2. **是否需要支持更新到特定版本而非最新版本？**
   - 当前设计：始终更新到 latest
   - 替代方案：支持命令行参数指定版本
   - 建议：当前需求不需要，可以作为未来增强功能

3. **是否需要记录更新历史？**
   - 当前设计：不记录历史
   - 替代方案：将更新记录写入日志文件
   - 建议：当前不需要，Volta 本身有版本管理
